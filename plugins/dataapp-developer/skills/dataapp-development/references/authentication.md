# Authentication

**Use this when:** you need to pick or configure an auth method for the app.

## Options overview

Keboola Data Apps ship with six built-in authentication methods. All of them
are configured on the app itself (in the Keboola UI, or via `modify_streamlit_data_app` /
`modify_python_js_data_app`)
and do not require any code changes inside the app.

- **None** — app is publicly accessible by URL. Implement your own auth in
  code if needed. Pick this if the app is a public demo or you want to handle
  auth at the application layer.
- **Basic Authentication** — Keboola-generated password (cannot be rotated).
  Pick this if you need a quick share with a small internal team and rotation
  is not a concern.
- **OIDC** — SSO via Auth0, Google Cloud, Microsoft Entra ID, or Okta. Pick
  this if your organization already runs one of these identity providers.
- **GitHub OAuth** — restrict access by organization, team, repository, or
  allowed users. Pick this if your audience is a developer org and access
  maps to GitHub membership.
- **GitLab OAuth** — restrict by groups, projects, or roles. Pick this if
  your audience lives in GitLab.
- **JumpCloud OIDC** — restrict by roles. Pick this if your org is managed
  via JumpCloud.

## When to pick which

| Situation                              | Auth                      |
|----------------------------------------|---------------------------|
| Public demo, no sensitive data         | None                      |
| Internal team, quick share             | Basic                     |
| Enterprise SSO already in place        | OIDC (matching provider)  |
| Developer org / repo restriction       | GitHub or GitLab          |
| JumpCloud-managed org                  | JumpCloud                 |

Note: "None" does not mean "no auth ever" — you can implement app-level auth (e.g. `streamlit_authenticator`) when you want custom logic that the six built-in methods do not cover.

## Callback URL format

All OAuth/OIDC methods use the same callback URL pattern:

```
https://<dataAppId>.hub.<keboolaConnectionHost>/_proxy/callback
```

Example:

```
https://my-app-12345678.hub.north-europe.azure.keboola.com/_proxy/callback
```

You must register this URL in the IdP's redirect URI configuration BEFORE deploying with that auth method. The `dataAppId` is shown in the app configuration after the first deployment, so the typical flow is:

1. Deploy the app once (with `basic-auth`) to obtain the `dataAppId`.
2. Configure the callback URL in the IdP.
3. Switch the app's auth method to the OAuth/OIDC provider.

With row-level security, set `runtime.workspace.rlsPolicies` in the same config change as step 3, then redeploy: a config with policies and a password login is refused. See [storage-access.md](storage-access.md) §Row-level security, "Turning row-level security on".

**Setting OIDC without the UI** (kbagent, Storage API). The login lives in the app config under `authorization.app_proxy`; Google shown, any OIDC provider has the same shape:

```json
{"auth_providers": [{"id": "google", "name": "Google", "type": "oidc",
                     "client_id": "<client id>", "#client_secret": "KBC::ProjectSecure::…",
                     "issuer_url": "https://accounts.google.com", "logout_url": "https://accounts.google.com/Logout"}],
 "auth_rules": [{"type": "pathPrefix", "value": "/", "auth_required": true, "auth": ["google"]}]}
```

Encrypt the secret before you write it (`POST https://encryption.<stack>/encrypt?componentId=keboola.data-apps&projectId=<id>`, body = the secret as `text/plain`); a config written outside the UI is stored as sent. Ask the user for the client ID and secret, never search for them.

## Basic auth gotcha

The password is **generated by Keboola at app creation and cannot be rotated**. To change it, the only path is:

1. Delete the app.
2. Recreate the app (which gets a new password).

If you need rotatable passwords, multiple users, MFA, or any kind of access auditing, use OIDC instead. Basic auth is best treated as a one-time shared secret for short-lived internal sharing.

## MCP defaults

When using `modify_streamlit_data_app` via MCP:

- **New apps** default to `basic-auth` for security if `authentication_type` is not specified.
- **Updates to existing apps** — pass `authentication_type="default"` to preserve the existing setup. Important: passing `"basic-auth"` on an UPDATE to an OIDC app will silently DOWNGRADE it to basic-auth. Always use `"default"` on updates unless you explicitly intend to change the auth method.

Acceptable values: `"no-auth"`, `"basic-auth"`, `"default"`. `"no-auth"` is only
for an app the user has explicitly asked to make public.

Rule of thumb: if you are not intentionally changing auth, set
`authentication_type="default"` on every update call. This is especially
important when the original auth was configured through the Keboola UI and
your update call is only adjusting other fields (env vars, secrets, size) —
omitting or hardcoding `authentication_type` is the most common cause of
accidental OIDC -> basic-auth regressions.

## Python/JS: a draft has the prod app's auth

A draft copies the prod app's config, authentication included, when it is created. It has no
authentication of its own to change. `"no-auth"` goes on the prod app only when the user has
explicitly asked to make the app public; a draft created after that is public at its own URL too,
with the same Storage access. Before you create a draft of a `no-auth` app, tell the user its draft
will be public too and create it only on their yes.

Never change `authentication_type` to get a preview to load. The preview link from
`get_data_app_preview_link` opens a draft whatever its auth (see `keboola/ui`
`apps/kai-agent/docs/data-apps-architecture.md`).

## Row-level data filtering pointer

Per-user / row-level data access is a storage-access concern, not an auth concern. In a workspace governed by row-level security, Query Service filters the rows by the signed-in user. The app only forwards the user token that Keboola's apps proxy adds after an OAuth/OIDC login; the React + Vite template does that by itself. Password login and no-auth apps get no token, so a governed workspace refuses their queries. See "Row-level security" in [storage-access.md](storage-access.md).
